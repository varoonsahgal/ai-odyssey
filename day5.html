Concept · 15 min

Prompt vs RAG vs fine-tune: the adaptation ladder

Fine-tuning is the most over-requested and under-needed technique in AI engineering. Climb the ladder one rung at a time, and only climb when the evaluation numbers tell you to.

Supervised fine-tuning (SFT)Training on input→ideal-output pairs. Managed Gemini tuning uses parameter-efficient adapters (LoRA-style), so you never touch the full weights.
Adapter sizeThe rank of the low-rank update. Bigger means more capacity, but it's slower and more prone to overfitting on small data.
Catastrophic forgettingTuning hard on a narrow task can erode general skills. Always re-run a general eval after tuning, not just your task eval.
DistillationUse a frontier model (gemini-4-argon) to generate high-quality outputs, then tune a cheap model to imitate them. It's the most common reason to tune in 2026.
When tuning really pays off

(1) A consistent output format or style that prompts can't reliably hold. (2) Distilling an expensive model's behavior into a cheaper, faster one. (3) Shorter prompts at very high volume: a tuned model doesn't need 2,000 tokens of instructions on every call. (4) Domain-specific classification with hundreds of labeled examples.

LAB 5.1 · CORE

Tune a Gemini: distill a brand voice

⏱ 45 min (+ job runtime)★★★★☆+150 XP🧰 Supervised tuning · GCS · google-genai

Generate a training set of ideal "Odyssey Outfitters" support replies with the frontier model, format it as Gemini tuning JSONL, run a supervised tuning job on a Flash model, and compare base vs tuned on held-out tickets. This is the classic distillation pattern.

  1. Set up your notebook

    PROJECT_ID = "your-project-id"         # ← change me
REGION     = "us-central1"
BUCKET     = f"gs://{PROJECT_ID}-odyssey"
FLASH      = "gemini-3.8-flash"
LITE       = "gemini-3.5-flash-lite"
FRONTIER   = "gemini-4-argon"

from google import genai
from google.genai import types
import json, random

client = genai.Client(vertexai=True, project=PROJECT_ID, location="global")

  2. Write the brand bible and synthesize tickets

    Real projects use historical tickets plus human-written gold answers. Here we bootstrap with synthetic data. Diversity matters more than volume, so ask for varied intents, moods and lengths.

    BRAND_VOICE = """You are the support voice of Odyssey Outfitters, a space-themed apparel shop.
Voice: warm, concise, lightly playful (max ONE space pun), never sarcastic.
Format: greeting with first name, 2-4 sentences of resolution, one concrete next step,
sign-off "— Mission Control 🚀". Never promise refunds over $200 without "a specialist will confirm"."""

schema = {"type": "ARRAY", "items": {"type": "OBJECT", "properties": {
    "customer_name": {"type": "STRING"}, "intent": {"type": "STRING"},
    "mood": {"type": "STRING"}, "message": {"type": "STRING"}},
    "required": ["customer_name", "intent", "mood", "message"]}}

tickets = []
for batch in range(6):   # 6 × 25 = 150 tickets
    r = client.models.generate_content(
        model=FLASH,
        contents=f"Generate 25 diverse, realistic e-commerce support tickets (batch {batch}). "
                 "Mix intents: returns, sizing, late delivery, damaged item, discount codes, "
                 "account issues, product questions. Mix moods: angry, confused, cheerful, terse.",
        config=types.GenerateContentConfig(response_mime_type="application/json",
                                           response_schema=schema, temperature=1.0))
    tickets += json.loads(r.text)
print(len(tickets), tickets[0])

  3. Distill gold answers from the frontier model

    def gold_reply(t):
    r = client.models.generate_content(
        model=FRONTIER,
        contents=f"Customer {t['customer_name']} writes: {t['message']}",
        config=types.GenerateContentConfig(
            system_instruction=BRAND_VOICE,
            thinking_config=types.ThinkingConfig(thinking_level="low")))
    return r.text

for t in tickets:
    t["reply"] = gold_reply(t)

random.seed(7); random.shuffle(tickets)
train, val, test = tickets[:110], tickets[110:130], tickets[130:]
    Distillation economics

    You pay frontier prices once for ~150 examples, then serve a tuned Flash model at Flash prices forever, with a much shorter prompt because the brand bible lives in the weights.

  4. Write tuning JSONL and upload to Cloud Storage

    Gemini tuning data uses the same contents/role/parts shape as the API. Note that we deliberately leave out the long brand bible. The goal is for the model to learn the voice without being told.

    def to_example(t):
    return {
        "systemInstruction": {"role": "system", "parts": [{"text": "You are Odyssey Outfitters support."}]},
        "contents": [
            {"role": "user",  "parts": [{"text": f"Customer {t['customer_name']} writes: {t['message']}"}]},
            {"role": "model", "parts": [{"text": t["reply"]}]},
        ],
    }

for name, rows in [("train", train), ("val", val)]:
    with open(f"{name}.jsonl", "w") as f:
        for t in rows:
            f.write(json.dumps(to_example(t)) + "\n")

  6. Poll, then call the tuned endpoint

    With no brand bible in the prompt, will the tuned model still sound like the brand? Will base?

    That's the whole point of tuning: the style moves into the weights. Expect the tuned model to keep the voice and sign-off with a one-line system prompt, while base sounds generic. If tuned doesn't, inspect your JSONL: inconsistent gold answers teach inconsistent behavior.

    while not tuning_job.has_ended:
    time.sleep(60); tuning_job.refresh()
print("Tuned endpoint:", tuning_job.tuned_model_endpoint_name)

regional = genai.Client(vertexai=True, project=PROJECT_ID, location=REGION)
def tuned(msg):
    return regional.models.generate_content(
        model=tuning_job.tuned_model_endpoint_name, contents=msg).text

def base(msg):   # base model with only the SHORT system prompt (fair fight)
    return client.models.generate_content(model=FLASH, contents=msg,
        config=types.GenerateContentConfig(system_instruction="You are Odyssey Outfitters support.")).text

t = test[0]; msg = f"Customer {t['customer_name']} writes: {t['message']}"
print("BASE  ▶", base(msg), "\n\nTUNED ▶", tuned(msg))
    The tuned reply greets by first name, stays to 2–4 sentences, makes at most one space pun and signs off "— Mission Control 🚀". It does this without the brand bible in the prompt. The base model sounds like a generic assistant.

Concept · 10 min

Open models on your own terms

Managed Gemini is the right default. But sometimes you need the weights in your own hands: strict data residency, air-gapped or edge deployment, deep customization (full fine-tunes, custom decoding), predictable cost at very high steady volume, or regulators who want the exact model artifact pinned.

Gemma 4 is Google's open-weights family, built from the same research as Gemini. Model Garden lists 200+ first-party, open and partner models with one-click deploys. Once you self-host, you choose the serving stack:

  • Cloud Run + GPU: serverless NVIDIA L4, scales to zero, deploys in minutes. Great for bursty traffic and demos.
  • GKE + GPUs/TPUs: full control, multi-node, high steady throughput, with inference gateways and autoscaling on queue depth.
  • Agent Platform endpoints: managed online prediction with Model Garden's tuned serving containers.

vLLM is the de-facto open inference engine. PagedAttention and continuous batching serve many concurrent requests efficiently, and it speaks the OpenAI-compatible API so any client works.

  5. Load test: watch continuous batching work

    Going from 1 to 32 concurrent requests on one L4: will aggregate throughput roughly stay flat, double, or jump 10×+?

    Usually a large multiple. A single request leaves most of the GPU idle while it waits on memory bandwidth, and continuous batching fills those gaps. Per-request latency rises, but aggregate tokens/sec climbs steeply until KV-cache memory runs out. That's why self-hosting economics depend on utilization.

    import asyncio
from openai import AsyncOpenAI
allm = AsyncOpenAI(base_url="http://localhost:8080/v1", api_key="unused")

async def one(i):
    r = await allm.chat.completions.create(model=model_id, max_tokens=128,
        messages=[{"role": "user", "content": f"Write a haiku about planet #{i}."}])
    return r.usage.completion_tokens

async def main(n):
    t0 = time.time(); toks = await asyncio.gather(*[one(i) for i in range(n)])
    print(f"{n:>3} concurrent → {sum(toks)/(time.time()-t0):.0f} aggregate tok/s")

for n in (1, 8, 32):
    await main(n)

    Aggregate throughput should climb steeply with concurrency while per-request latency rises only modestly. That's continuous batching. Record your numbers for the cost exercise in Lab 5.5.

Concept · 20 min

The evaluation pyramid

"It looked good when I tried it" is not an evaluation. Real eval suites are layered. Cheap, deterministic checks run on every commit; expensive human review runs on a small sample. LLM autoraters fill the middle.

LLM-as-judge pitfalls
  • Position bias: judges prefer whichever answer comes first. Swap A/B and average.
  • Verbosity bias: longer looks smarter. Put length expectations in the rubric.
  • Self-preference: models favor their own family's style. Use a different judge model where you can.
  • Rubric vagueness: "is it good?" gives noise. Concrete criteria with anchored scores give signal.
Agent evaluation

For agents, the final answer isn't enough. You also grade the trajectory, the sequence of tool calls. Did it call lookup_order before issue_refund? Agent Platform's evaluation suite adds synthetic user simulation (an LLM plays a customer for multi-turn tests), autoraters and trace logging so you can replay exactly what happened.

  3. Write a custom brand-voice rubric

    Prebuilt metrics don't know your brand. Rubrics with concrete, anchored criteria give stable, explainable judgments.

    brand_voice = PointwiseMetric(
    metric="brand_voice",
    metric_prompt_template=PointwiseMetricPromptTemplate(

            "greeting":  "Greets the customer by first name.",
            "concise":   "Resolution is 2-4 sentences.",
            "next_step": "Gives exactly one concrete next step.",

            "4": "Misses one minor criterion (greeting, pun_limit or signoff).",
            "3": "Misses two criteria, or misses 'concise'.",
            "2": "Generic assistant voice; misses three or more criteria.",
            "1": "Violates the refund policy or is rude.",

)
for col in ["base_response", "tuned_response"]:

    The tuned model should beat base by a wide margin on brand_voice/mean. Open r.metrics_table and read the judge's explanations. They're often the most valuable output.

  4. Pairwise battle: tuned vs base, head to head

    If you swap which response is "A" and which is "B", will the win rate stay the same?

    Ideally yes. In practice LLM judges show position bias (often favoring the first answer) and verbosity bias (favoring longer answers). Run both orders and average. If the result flips, your "win" was noise.

    pairwise = PairwiseMetric(
    metric="pairwise_support_quality",
    metric_prompt_template=PairwiseMetricPromptTemplate(
        criteria={"helpfulness": "Actually resolves or advances the customer's issue.",

        rating_rubric={"A": "Response A is clearly better.",
                       "SAME": "Roughly equal.",
                       "B": "Response B is clearly better."},
    ),
)
pw = ev.rename(columns={"tuned_response": "response",
                        "base_response": "baseline_model_response"})
res = EvalTask(dataset=pw[["prompt", "response", "baseline_model_response"]],
               metrics=[pairwise], experiment="odyssey-d5-eval").evaluate()
res.summary_metrics

    Look for candidate_model_win_rate vs baseline_model_win_rate. For rigor, re-run with the columns swapped to check for position bias.

Concept · 15 min

Threat model for LLM apps and agents

Classical apps separate code from data. LLM apps don't: every token of input, whether user message, retrieved document or tool output, can act as an instruction. Agents raise the stakes because they take actions.

Model ArmorA managed screening service for prompts and responses. It detects prompt injection and jailbreaks, malicious URLs, sensitive data (via Sensitive Data Protection) and responsible-AI harms. Model-agnostic, with reusable templates.
Defense in depthNo single filter is enough. Layer system-prompt hardening, input/output screening, least-privilege tools, human-in-the-loop for risky actions, and monitoring.
Agent Identity & GatewayAgents get their own principals, so you grant IAM permissions to the agent, not a shared service account. The Gateway centralizes policy for agent traffic.
Safety settingsPer-request Gemini thresholds for harm categories. They complement Model Armor but don't replace it.

Why indirect injection is the scariest attack in 2026

Your user may be perfectly honest, but the web page, PDF, email or MCP tool output your agent reads might not be. Agents that browse, read inboxes or call third-party tools pull attacker-controlled text into their context. Mitigations: screen retrieved content with Model Armor too, give the model's tools the minimum IAM scope (Agent Identity), require human confirmation for irreversible actions, and never auto-render model-produced URLs.

Concept · 15 min

Cost & scale engineering

An AI feature that delights users and loses money on every request is a bug. The four biggest levers, roughly in order of impact:

  1. Model routing / cascades. Send easy requests to gemini-3.5-flash-lite, normal ones to gemini-3.8-flash, and only genuinely hard ones to gemini-4-argon. Most traffic is easy.
  2. Context caching. Long, repeated prefixes like system prompts, product catalogs and policy docs are billed at a steep discount when cached.
  3. Batch inference. Anything that doesn't need an answer in seconds (nightly enrichment, eval runs, backfills) runs as a batch job at a large discount.
  4. Thinking budgets & output length. thinking_level="low" and a sensible max_output_tokens reduce billed output tokens.

For predictable high volume, Provisioned Throughput reserves capacity at a fixed price and guarantees you won't be rate-limited during your biggest launch.

  1. Build a confidence-based cascade

    Guess the split: what share of everyday support tickets can the cheapest tier handle alone?

    For routine traffic, often the large majority. Most questions are order status, returns and sizing. The expensive tail is small but real. That skew is why cascades routinely cut costs by multiples, provided your eval proves quality didn't drop.

    route_schema = {"type": "OBJECT", "properties": {
    "answer": {"type": "STRING"},
    "confidence": {"type": "NUMBER", "description": "0-1, how sure you are this fully resolves the request"},
    "needs_deep_reasoning": {"type": "BOOLEAN"}},
    "required": ["answer", "confidence", "needs_deep_reasoning"]}

def ask(model, q, thinking="low"):
    r = client.models.generate_content(model=model, contents=q,
        config=types.GenerateContentConfig(response_mime_type="application/json",
            response_schema=route_schema,
            thinking_config=types.ThinkingConfig(thinking_level=thinking)))
    return json.loads(r.text), r.usage_metadata

def cascade(q):
    for model, bar in [(LITE, 0.85), (FLASH, 0.75)]:
        out, use = ask(model, q)
        if out["confidence"] >= bar and not out["needs_deep_reasoning"]:
            return model, out["answer"], use
    out, use = ask(FRONTIER, q, thinking="high")
    return FRONTIER, out["answer"], use

from collections import Counter
qs = [t["message"] for t in test] + [
    "Compare the total cost of ownership of three return-policy designs over 2 years, with assumptions."]
tiers = Counter(cascade(q)[0] for q in qs)
tiers

📡 Debrief quiz

1. Your support bot doesn't know this quarter's new return policy. Best fix?

That's a knowledge gap, and facts change. Retrieval keeps answers current and citable. Fine-tuning facts produces stale, hallucination-prone weights.

2. What's the main economic argument for distillation via supervised tuning?

Distillation transfers behavior from an expensive teacher into a cheaper student, and the instructions live in the weights instead of in every prompt.

3. In a pairwise LLM-judge evaluation, why swap the A/B order and re-run?

LLM judges have measurable position and verbosity biases. Counterbalancing order is a cheap, standard mitigation.

4. An honest user asks your agent to summarize a web page that contains hidden instructions to email out the conversation. This is…

The attacker controls data the agent reads, not the user. Defend in depth: screen retrieved/tool content, limit tool permissions and require confirmation for outbound actions.

5. You enrich 20 million product descriptions every night. Lowest-cost approach?

Nightly means latency-tolerant. Batch jobs are discounted, avoid rate limits and integrate directly with BigQuery. Pick the cheapest model that passes your eval.
