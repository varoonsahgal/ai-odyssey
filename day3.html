Concept · 15 min

Inside a 2026 LLM

You don't need to train a frontier model to use one well, but you do need a working mental model. Every behavior you'll see today comes from the pipeline below: cost, latency, the "thinking" pause, why images are expensive and why JSON mode works.

TokenThe unit of everything: billing, context limits, latency. Roughly ¾ of an English word. Images, audio and video become tokens too.
Thinking levelHow much hidden reasoning the model does before answering. Higher means better on hard problems, but slower and costlier.
Mixture-of-ExpertsA sparse architecture where a router sends each token to a few specialist sub-networks. It's how frontier models get huge without huge per-token cost.
Constrained decodingWhen you pass a schema, the decoder can only emit tokens that keep the output valid. That's why it beats "please reply in JSON".
GroundingAnchoring an answer to retrieved evidence (web, your data) and returning citations, the main antidote to hallucination.
TemperatureSampling randomness. Low for extraction and classification, higher for brainstorming and creative work.

  4. The thinking-level showdown

    Give three models the same puzzle at different thinking levels. Measure latency, thinking tokens and correctness.

    import time, pandas as pd

PUZZLE = """A probe leaves Io at 09:00 travelling 12 km/s toward Europa.
A second probe leaves Europa at 09:20 travelling 9 km/s toward Io.
Io and Europa are 249,000 km apart (assume fixed). At what clock time
do they meet, to the nearest minute? Answer with just the time."""

rows = []
for alias in ["LITE", "FLASH", "FRONTIER"]:
    for level in ["low", "high"]:
        t0 = time.perf_counter()
        try:
            r = client.models.generate_content(
                model=MODELS[alias], contents=PUZZLE,
                config=types.GenerateContentConfig(
                    thinking_config=types.ThinkingConfig(thinking_level=level)),
            )
            u = r.usage_metadata
            rows.append(dict(model=alias, level=level,
                             secs=round(time.perf_counter() - t0, 1),
                             thoughts=u.thoughts_token_count or 0,
                             output=u.candidates_token_count,
                             answer=r.text.strip()[:40]))
        except Exception as e:
            rows.append(dict(model=alias, level=level, answer=f"⚠ {e}"[:60]))
pd.DataFrame(rows)
    Before you run it: which configuration is the cheapest one that still gets the right time?

    Most teams bet on Frontier/high. The interesting answer is usually much lower in the table. A Flash model with thinking turned up often handles the head-start trap, and Flash-Lite/low often falls for it. The point of the exercise is to find the cheapest correct row, not the smartest model.

    Thinking tokens and latency climb with level. Not every configuration gets the right time, and the puzzle has a trap (probe B leaves 20 minutes late). Compare each answer to the solution below and note the cheapest configuration that gets it right.
    The answer (no peeking until your table is filled)

    By 09:20 probe A has flown 12 km/s × 1,200 s = 14,400 km, leaving 234,600 km. The closing speed is 21 km/s, so they meet 11,171 s ≈ 186 min after 09:20, at 12:26. Models that skip the head start usually answer 12:17 or 12:18. Always verify model arithmetic, or give the model a code-execution tool (Lab 3.4).

    API drift check

    Gemini 3+ models use thinking_level. Some lighter models accept only a subset of levels, so the try/except records that instead of crashing. Older tutorials use thinking_budget (a token count). Check the model card for what each model supports.

Concept · 20 min

Prompt patterns that still matter in 2026

Models got smarter, and "prompt engineering" tricks like magic phrases mostly died. What survived are software engineering patterns for talking to a probabilistic component:

  1. System instruction = contract. Role, audience, constraints, refusal behavior, output format. Version it like code.
  2. Schemas over parsing. Never regex a model's prose. Pass a Pydantic model as response_schema and get valid JSON via constrained decoding.
  3. Few-shot for style, not facts. Two or three examples teach tone and edge-case handling better than paragraphs of rules.
  4. Decompose. One call that researches, reasons, formats and translates is fragile. Four small calls are testable.
  5. Put long context first, question last. For big documents, place the material before the instructions.
  6. Give an "out". Allow "unknown" or null in your schema, otherwise the model invents a value to satisfy it.
Pattern #6 in action

An invoice schema with a required invoice_number: str applied to a receipt that has no number will "find" one, usually by fabricating something plausible. Make it invoice_number: str | None and add "use null if absent" to the field description. Field descriptions are prompts too.

  2. Design the schema (this is the prompt)

    from enum import Enum
from pydantic import BaseModel, Field

class Currency(str, Enum):
    USD = "USD"; EUR = "EUR"; GBP = "GBP"; OTHER = "OTHER"

class LineItem(BaseModel):
    description: str
    quantity: float
    unit_price: float
    amount: float = Field(description="quantity × unit_price as printed on the invoice")

class Invoice(BaseModel):
    vendor_name: str
    invoice_number: str | None = Field(description="null if not printed")
    invoice_date: str | None = Field(description="ISO 8601 YYYY-MM-DD, null if absent")
    currency: Currency
    line_items: list[LineItem]
    subtotal: float | None
    tax: float | None
    total: float
    confidence: float = Field(ge=0, le=1, description="your confidence the extraction is fully correct")

  3. Extract one invoice

    EXTRACT_CFG = types.GenerateContentConfig(
    system_instruction="You are a meticulous accounts-payable clerk. Extract exactly what is printed.",
    response_mime_type="application/json",
    response_schema=Invoice,
    temperature=0,
    thinking_config=types.ThinkingConfig(thinking_level="low"),
)

def extract(uri: str) -> Invoice:
    r = client.models.generate_content(
        model=MODELS["FLASH"],
        contents=[types.Part.from_uri(file_uri=uri, mime_type="application/pdf"),
                  "Extract this invoice."],
        config=EXTRACT_CFG,
    )
    return r.parsed   # the SDK returns a validated Invoice instance

inv = extract(f"{BUCKET}/d3/invoices/invoice_00.pdf")
print(inv.model_dump_json(indent=2))
    Predict: will the model ever return a currency outside your Enum, or a string where you asked for a float?

    With response_schema, decoding is constrained: the model can only emit tokens that keep the JSON valid against your schema. Types and enums hold. What can still be wrong is the content, like a misread total. That's why the next steps score accuracy, not just validity.

    A fully typed Invoice object. r.parsed is already a Pydantic instance, so there's no json.loads, no regex and no "Sure! Here's your JSON:" preamble.

    score = []

Concept · 20 min

Multimodal tokens & context caching

Gemini is natively multimodal. Images, audio and video frames become tokens in the same sequence as text, so the model can reason across them ("at what timestamp does the speaker contradict the slide?").

That means media has a token cost. As rough orders of magnitude at default settings: an image is a few hundred tokens, a second of video a few hundred (frames are sampled at ~1 fps plus audio), and a second of audio a few dozen. A one-hour video can approach a million tokens. Always measure with count_tokens and use media_resolution to trade detail for cost.

Context caching fixes the "same giant prefix, many questions" problem. Upload the 1-hour video or 500-page manual once, cache it with a TTL, then send only the short question each time. Cached input tokens are billed at a steep discount, plus a small per-hour storage fee.

The caching break-even formula

Caching wins when N × P × (price_in − price_cached) > P × price_in + P × storage_per_hour × hours, where N is the number of queries in the TTL and P the prefix tokens. With typical discounts it breaks even after just a handful of reuses. Gemini also applies implicit caching automatically to repeated prefixes. Explicit caches give you a guaranteed hit and a fixed TTL.

  1. Write two tools as plain Python functions

    The SDK turns type hints and docstrings into a function declaration, so the docstring is the tool's prompt.

    from google.cloud import bigquery
import uuid
bq = bigquery.Client(project=PROJECT_ID)

def get_churn_risk(user_id: int) -> dict:
    """Look up a customer's churn probability and the top reasons behind it.

    Args:
        user_id: The numeric customer ID from the e-commerce database.
    """
    q = """SELECT churn_prob, top_feature_attributions
           FROM `odyssey_d1.churn_explained` WHERE user_id = @uid"""
    job = bq.query(q, job_config=bigquery.QueryJobConfig(
        query_parameters=[bigquery.ScalarQueryParameter("uid", "INT64", user_id)]))
    rows = list(job.result())
    if not rows:
        return {"error": f"user {user_id} not found"}
    r = rows[0]
    return {"churn_prob": r.churn_prob,
            "reasons": [{"feature": a["feature"], "attribution": round(a["attribution"], 3)}
                        for a in r.top_feature_attributions]}

def issue_coupon(user_id: int, percent_off: int) -> dict:
    """Issue a one-time retention coupon. Policy: percent_off must be 5–25.

    Args:
        user_id: The customer receiving the coupon.
        percent_off: Discount percentage between 5 and 25.
    """
    if not 5 <= percent_off <= 25:
        return {"error": "policy violation: percent_off must be 5-25"}
    return {"code": f"ODY-{uuid.uuid4().hex[:6].upper()}", "percent_off": percent_off}

Concept · reference

Cost & safety levers

💸 Six cost levers, in order of impact

  1. Route by difficulty. Flash-Lite → Flash → Argon. Most traffic should never reach the top tier.
  2. Turn thinking down for extraction and classification. Thinking tokens are output tokens.
  3. Cap output with max_output_tokens and tight schemas.
  4. Cache big repeated prefixes (explicit or implicit caching).
  5. Batch anything not latency-sensitive. Batch prediction is substantially cheaper than online.
  6. Provisioned Throughput for predictable high-volume workloads that need guaranteed capacity.

BOSS BATTLE · DAY 3

🐉 The Hallucination Hydra

Cut off one false claim and two more grow back. Your team must build a Mission Briefing Generator: given a photo, a PDF and a topic, it returns a schema-valid JSON briefing where every claim is cited, plus a generated mission poster. The Hydra wins if a single fabricated fact gets through.

Victory conditions (check each to deal damage)

  • Schema-valid 10/10: your Briefing Pydantic model validates on 10 consecutive runs with different inputs.
  • Zero uncited claims: every factual sentence carries a citation (a web source from grounding_metadata, or [p.N] from the PDF). A rival team audits five briefings.
  • Hydra-proof: given a false-premise topic like "Why does Jupiter have no moons?", the system corrects the premise instead of inventing an answer.
  • Poster generated with an image model, visually consistent with the input photo and carrying the briefing's title.
  • Cost per briefing under $0.05 (excluding the poster), computed from usage_metadata and current list prices, shown in a table.
Hydra-slaying hints
  • Two-stage pipeline. Stage 1 does grounded research with the Google Search tool and returns free text plus grounding_metadata. Stage 2 is a cheap structured call that turns stage-1 text and the PDF into your schema, carrying citations through. Combining search grounding and strict schemas in one call can be restricted. Splitting is also easier to test.
  • Put a citations: list[str] field on every claim object in your schema, not just once at the end.
  • Add premise_check: str | None to the schema with the description "if the topic contains a false assumption, explain it here".
  • Use LITE for the stage-2 formatting call. That's where you win the cost criterion.
class Claim(BaseModel):
    text: str
    citations: list[str] = Field(min_length=1, description="URLs or [p.N] page refs")

class Briefing(BaseModel):
    title: str
    premise_check: str | None
    situation: list[Claim]
    risks: list[Claim]
    recommended_actions: list[str]
    poster_prompt: str

📡 Debrief quiz

1. What's the most reliable way to get machine-readable output from Gemini?

A schema enables constrained decoding: the model can only emit tokens that keep the output valid. Prompts request, schemas enforce.

2. You raise thinking_level from LOW to HIGH. What should you expect?

Thinking tokens are hidden reasoning billed like output tokens. It's worth it for hard reasoning and wasteful for simple extraction.

3. Users ask about news from this morning. Best fix?

Fresh public facts are a grounding problem. Fine-tuning teaches behavior, not up-to-the-minute knowledge.

4. A 400-page manual is queried ~2,000 times per hour. Biggest single cost lever?

The manual is a huge repeated prefix, which is exactly what caching is for. Streaming improves perceived latency, not cost.

5. Your issue_coupon tool must never exceed 25% off. Where should that rule live?

Prompts guide, code enforces. Models can be persuaded or make mistakes, so hard business rules belong in deterministic code.
